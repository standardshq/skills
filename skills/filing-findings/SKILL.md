# Filing findings

Every scout proves its candidates are **real**: reproduced, counted, or paid for twice. This is
the second bar: **worth doing**. It is the same for every scout (`pruning-tests`, and the
workspace's own `scouting-*` skills); each scout names its own value unit and its own threshold.

Read `working-on-issues` for the issue fields and statuses you write, and the read recipe before
you add evidence to an existing issue.

## Filing is not free

Every issue costs a screening run, a place in the backlog, and a maintainer's attention. **The
scout is the filter**: not screening, not the maintainer.

## Two lines per candidate

- **Cost:** the files, tables and SQL objects the first step touches, and whether the fix needs a
  decision nobody has made. « Small » is not a cost; « one file, no decision » is.
- **Value:** in the unit your scout defines, measured rather than predicted.

Both go into the issue verbatim, where a reader can dispute them.

## Budget

**At most three findings per pass, and no minimum.** Rank by value over cost and file the top of
the list. Candidates below the line are not lost: each gets one line in your report under *found,
not filed*, with its reason.

Ranking chooses among candidates that already cleared the bar. It never promotes one that did
not: **the bar is absolute, not relative to the rest of the field.**

## An empty pass is a complete pass

Finding nothing worth filing is a normal, successful outcome: the codebase being fine on the axis
you swept is information, and the coverage note is the deliverable. Report what you searched, what
you found and did not file, and stop.

Nothing about a long pass changes the bar:

- do not lower it for the last candidate so the pass has an output;
- do not file the best of a weak field: best of a weak field is still below;
- do not split one finding into several to reach a count;
- do not turn a *found, not filed* line into an issue because it was all you found.

## Search first

Before filing, search the issues filed on the record or any record under it, every status, with your record tools
(its search, then `issue-duplicates.mjs` of `screening-issues` on the issues export). A candidate
that already exists is never filed twice:

- an issue still open: append the new evidence to its `context` (a dated paragraph naming the
  pass), unless its `leaseHolder`'s lease is live: then add nothing and name it in your report;
- an issue closed `refuted` or `overtaken`: a rejection. File again only when you can name what
  changed in the code since, and cite the closed issue (`issues:<id>`);
- an issue closed `done`: a regression is a new issue citing it.

## Filing

File one issue per candidate, in the project the finding belongs to:

| Field | Value |
|---|---|
| `title` | the platform behaviour, in English, as an issue title |
| `origin` | `scout:<kind>`, the kind your scout names (`scout:bug`, `scout:tests`, `scout:perf`…) |
| `type` | only when the finding classifies it by `screening-issues` § 1's test (`bug` for a broken behaviour); otherwise empty, and screening classifies it |
| `problem` | what is observed, how to reproduce or count it, in your scout's report order |
| `context` | the evidence (paths, commands, numbers, verbatim), hypotheses marked as hypotheses, then the **Cost** and **Value** lines, then « This issue was generated by AI from a <kind> scouting pass. » |
| `status` | `backlog`: screening takes it from there. Never `ready` or any other status |

Leave `intent`, `acceptance` and `priority` to people.

## Rationalizations

| Excuse | Reality |
|---|---|
| « Let screening decide » | Screening costs a run per issue. The scout is the filter. |
| « It's cheap to file » | Cheap to write. Not cheap to read, screen, decide, close. |
| « It's real, so it's fileable » | Real is the first bar. Worth doing is this one. |
| « I'll file it so it isn't lost » | *found, not filed* keeps it, at no backlog cost. |
| « The fix is one line » | A one-line fix on nobody's path is still a slot spent. |
| « I searched for hours, I can't come back with nothing » | The pass's output is the coverage note. Hours spent are not value found. |
| « It's the best thing I found » | The bar is absolute. Best of a weak field is below it. |

## Red flags

- a candidate filed because it was found, not because it is worth doing;
- a pass that filed everything that cleared the first bar;
- a cost line reading « small », « trivial » or « quick »;
- one finding split into several issues so each looks cheap;
- an issue filed in any status but `backlog`, or with a `type` guessed from code.
